# 第一阶段小结：P0～P2 基础建设完成

## 一句话总结

Enterprise Data Copilot 已经完成从“想法”到“可靠地基”的建设：项目目标和安全边界已经明确，Java、Python、Web 三部分可以独立运行，Docker 中的数据库和 Redis 可以一键启动，并且已经有一套固定、只读、可检查的 Northwind 零售数据。

目前系统还不会根据自然语言自动生成分析答案，但后续实现这项能力所需要的工程骨架、数据和安全底线已经准备好。

## 项目要解决什么问题

这个项目面向不熟悉 SQL 的业务分析人员。最终用户可以直接提出类似下面的问题：

- 2025 年每个月的销售额是多少？
- 哪些客户贡献的销售额最高？
- 哪类商品销量最好？

系统会把自然语言问题转换成安全的只读查询，并返回文字结论、数据表、图表、SQL 和引用依据。

它不是一个可以随意操作数据库的通用机器人。即使 AI 生成了危险指令，最终也必须经过程序规则和数据库权限检查。

## P0：先确定做什么、不做什么

P0 没有急着写业务代码，而是先把项目范围收紧。

这一阶段确定了：

- 首版只分析 Northwind 零售数据，不承诺支持所有行业和数据库。
- Java 负责登录、租户、权限、任务、审批和审计。
- Python 负责元数据检索、AI 工作流、SQL 生成和安全检查。
- Web 只和 Java 通信，不能直接连接 Python 或业务数据库。
- AI 没有写数据库的权限，也不能执行任意 Python、Shell 或 JavaScript。
- 危险 SQL、跨权限访问和证据不足的问题必须拒绝、暂停或要求澄清。

通俗地说，P0 完成的是“画图纸、划红线、确定验收题目”。这避免了后面一边开发一边不断改变项目方向。

## P1：把项目骨架搭起来

P1 建立了三个可以独立运行的程序：

| 程序 | 通俗作用 | 当前能力 |
|---|---|---|
| Java Platform API | 企业系统的门卫和总管 | 健康检查、任务状态规则、数据库迁移基础 |
| Python Agent Service | 未来负责分析和生成 SQL 的分析员 | 健康检查、内部接口契约、配置与测试基础 |
| Next.js Web | 用户以后提问和看结果的页面 | 基础页面、健康检查、构建与代码检查 |

同时，Docker 中准备了三个基础容器：

| 容器 | 通俗作用 |
|---|---|
| `platform-db` | 保存用户、任务、权限、审批和审计等平台数据 |
| `business-db` | 保存被分析的 Northwind 销售数据 |
| `redis` | 以后临时保存任务进度、缓存和幂等信息 |

P1 还提前确定了 Java 与 Python 之间的接口格式、任务状态变化规则和事件字段。这样后续增加真实业务时，不需要反复推翻接口。

## P2：准备真实可验证的数据底座

P2 建立了固定版本 `northwind-compact-v1`，其中包括：

- 8 张业务表；
- 10 个客户；
- 12 种商品；
- 20 张订单；
- 40 条订单明细；
- 覆盖 2024 和 2025 年的销售日期。

这是一份适合当前开发和自动化测试的精简 Northwind 兼容数据，不冒充完整的官方生产数据。固定版本的好处是：同一个问题每次测试都应得到相同结果，程序出现变化时更容易定位原因。

### 数据库安全

程序查询业务数据时使用 `northwind_reader` 账号。这个账号：

- 可以读取 `northwind` 区域中的业务表；
- 不能创建、修改或删除表和数据；
- 不能读取专门用于测试边界的 `restricted` 区域；
- 单条查询超过 2 秒会被数据库取消。

这意味着只读限制不是写在提示词里提醒 AI，而是由 PostgreSQL 直接执行。即使上层程序以后出现错误，数据库仍然会拒绝写入。

### 自动认识数据库结构

Python 现在可以自动读取数据库的“目录”，包括：

- 有哪些表；
- 每张表有哪些字段；
- 字段是什么类型、是否允许为空；
- 表和字段的说明；
- 哪些字段是主键；
- 表之间通过哪些外键连接。

程序只保存这些结构摘要，不读取并保存整张业务表的样例数据。结构摘要带有 SHA-256 版本号和缓存有效期，数据库结构变化后可以被自动发现。

### 第一批标准问题

项目已经建立 15 条中文 gold case，例如客户销售额排名、月度销售额、商品销量、平均订单金额和未发货订单。

每道题包含：

- 用户问题；
- 标准 SQL；
- 应返回的字段；
- 题目涉及的能力标签。

这些题不是用来证明 AI 已经会生成 SQL，而是作为后续 P5、P10 衡量准确率的固定试卷。目前测试已经证明这 15 条标准 SQL 都能在只读账号下正确执行。

## 当前已经能做到什么

- 一条命令启动两个 PostgreSQL 和一个 Redis。
- 启动 Java、Python、Web 三个程序并检查它们是否正常运行。
- 重复装载同一版本的 Northwind 数据。
- 使用真正的只读账号连接业务数据库。
- 自动提取数据库结构摘要并与固定快照比较。
- 在测试程序中执行 15 条标准只读 SQL。
- 自动验证写入、跨 schema 和超时查询会失败。
- 在数据库不可连接时返回稳定错误，避免把密码和连接地址暴露给用户。

## 当前还不能做到什么

- 用户还不能登录或区分不同租户。
- Java 还没有正式的数据源、任务和审计业务表。
- Python 还没有接入真实或模拟大模型。
- 系统还不能把自然语言自动转换为 SQL。
- SQL AST 安全检查、表字段白名单和结果数量限制还没有实现。
- Web 还不是最终的分析操作页面。
- 还没有 RAG 指标知识库、人工审批、异步任务和 SSE 实时进度。

明确写出这些未完成功能很重要：当前完成的是可靠的数据和工程基础，不把后续能力描述成已经完成。

## 这一阶段带来的价值

完成 P0～P2 后，项目已经避免了几个常见问题：

1. **范围失控**：先限定零售分析和 Northwind，不追求万能 Agent。
2. **服务职责混乱**：Java 管企业规则，Python 管 AI 分析，二者边界明确。
3. **只靠 AI 自觉**：数据库账号本身没有写权限，安全不依赖提示词。
4. **测试结果无法复现**：数据、结构快照和评测问题都有固定版本。
5. **把整库数据发给模型**：当前只提取必要的 schema 摘要。
6. **简历数字无法证明**：所有完成数字都能对应到测试命令和验收记录。

## 下一步

按照收敛版路线，下一步先完成“无模型安全纵向切片”：使用一条固定 SQL，依次经过安全检查、只读执行、结果限制和审计记录。

这一步会先证明整个安全执行链路可以工作，再继续 P3 的身份、租户和任务平台，以及 P4、P5 的模型接入和自然语言转 SQL。这样可以把数据库问题、安全规则问题和模型问题分开验证。
