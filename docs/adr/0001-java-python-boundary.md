# ADR-0001：分离 Java 平台服务与 Python Agent 服务

- 状态：Accepted
- 日期：2026-09-13
- 决策者：项目维护者

## 背景

项目既有典型企业平台职责（身份、租户、RBAC、审批、审计、幂等和事务），又有快速变化的 AI 工作流职责（模型适配、RAG、NL2SQL、LangGraph 和评测）。如果全部放在一个服务中，边界更少，但权限、状态所有权和技术迭代会互相牵连。

## 决策

采用两个可独立部署但不对等的服务：

- **Java Platform API 是外部入口和业务状态权威源**，拥有身份、租户、角色、数据源登记、任务、审批、审计和浏览器 API。
- **Python Agent Service 是内部受信调用方**，拥有模型适配、检索、分析计划、SQL 生成、确定性 SQL guard、受限查询执行和答案编排。
- 浏览器只能访问 Java。Java 调用 Python 时携带服务令牌、由登录态导出的租户/用户/角色声明、`Idempotency-Key` 和 `traceparent`。
- Python 不从请求体中的任意浏览器字段推断租户身份，也不成为审批状态的权威来源。
- 平台数据库与业务数据库使用不同连接、账号和权限；查询执行器只使用业务库只读账号。

## 为什么这样分

Java 侧的规则相对稳定，适合承载强类型业务模型、Spring Security、事务和企业集成。Python 侧的 AI 库和模型生态变化快，适合快速替换 provider、检索策略和图工作流。分离后，AI 服务可以失败或升级而不改变外部鉴权与审计语义，平台层也不会获得绕过 SQL 安全边界的捷径。

## 被否决的方案

### 全部使用 Python

优点是初期开发快、部署单一；缺点是不能体现目标岗位需要的 Java 企业后端能力，并容易让 Agent 流程与身份、审批和任务事务混在一起。当前不采用。

### 全部使用 Java

优点是统一技术栈；缺点是 LangGraph、模型评测和 Python 数据工具生态的集成成本更高，实验速度较慢。当前不采用。

### 浏览器直接调用 Python

能减少一次网络跳转，但会产生两个外部鉴权入口，并让租户身份、任务状态和审计更难保持一致。明确禁止。

### 一开始使用消息队列解耦

消息队列适合规模化异步执行，但 P0/P1 尚未证明同步契约和状态机。过早引入会增加幂等、重试、死信和运维成本。先使用内部 REST；达到吞吐或可靠性证据后再单独写 ADR。

## 后果

### 正面

- 企业业务权限与模型行为之间存在清晰的信任边界。
- 两侧可独立测试、扩容和替换技术组件。
- Java/Python 能分别展示目标岗位相关的工程能力。
- 审批、审计和租户规则不依赖模型是否正常工作。

### 代价

- 需要维护内部 API 合约、跨服务错误映射和 trace 传播。
- 任务状态存在跨进程协调，需要明确定义权威源、幂等和补偿。
- 本地开发和 CI 至少包含两个后端构建系统。

## 强制约束

- 内部接口必须版本化并由 OpenAPI/契约测试覆盖。
- Java 保存任务最终状态；Python 返回结构化步骤和结果，不直接接受浏览器状态更新。
- Python 的数据库访问必须通过唯一受限执行器，禁止节点自行创建任意连接。
- SQL 是否安全由确定性规则和数据库权限决定，不由模型自评决定。
- 日志不得包含服务令牌、模型密钥、完整 DSN 或未经策略允许的业务结果。

## 复审触发条件

- 内部 REST 成为可测量的吞吐或可靠性瓶颈。
- 团队维护两种语言的成本超过独立演进收益。
- 出现需要长时间离线处理、跨区域执行或可靠队列语义的明确需求。
